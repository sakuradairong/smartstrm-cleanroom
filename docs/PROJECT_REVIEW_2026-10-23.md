## 还需针对性验证的风险

- 批量重命名使用原请求 context 回滚，并忽略回滚错误。客户端取消或远端操作失败时，可能遗留 `.smartstrm-*` 文件；目前测试只覆盖成功交换。建议独立有界恢复 context、返回未恢复清单，再评估持久事务日志。
- `withRuntime` 在远端列目录、批量重命名和 ffmpeg 提封面全程持读锁。长操作会延迟配置提交；应让请求持不可变运行态快照，只在短暂发布时加锁，同时保留写入归属控制。
- 代理退出由后台 goroutine 执行，main 仅等待管理 HTTP 的 shutdown。Go 进程退出可能早于代理排空；还需在真实慢流和 WebSocket 上验证，包括强制关闭策略。
- 配置读取将 `restart_required` 固定为 false，前端首次 load 也未恢复该状态；刷新后会丢失待重启提示。需要同时显示磁盘期望、有效配置与待重启字段。
- 历史 SSE 先取快照后订阅存在漏事件窗口；慢订阅者溢出时静默丢弃，忽略 Last-Event-ID。若其定位为完整审计流，需要序号补读和丢失提示；若仅实时观察，应明确语义。
- 本地列表会跟随根内目录符号链接，生成递归没有循环检测；历史记录达到上限后每条事件重写整个文件；123 路径与 File ID 解析重复列父目录。应分别补循环、事件吞吐和请求预算测试。
- 前端存储表 `pagination=false` 且无虚拟列表；OpenList 列表允许十万项。大目录会带来响应内存、排序和 DOM 压力，当前小样本单测无法证明容量。
- Basic Auth 用户名为空时明确关闭认证，配置验证允许该状态。是否继续支持应形成明确产品决定，不能把所有部署都描述为强制管理认证。

## 架构判断

适合继续保持 Go 单体。主要问题是跨任务、跨运行代、跨前后端的隐含不变量没有集中表达，拆成微服务会增加协调成本。

现有值得保留的设计包括：Storage 与可选 FileIDStorage/HTTPStreamer 接口、多驱动协议测试、元数据大小上限、签名验证、生成失败时禁止同步删除、配置原子持久化、前端分页面懒加载。文件行数只用于定位审查热点，不作为重构理由。

建议形成以下三个深模块，内部可以继续拆文件，但外部接口隐藏复杂规则：

| 模块 | 调用方需要的最小接口 | 应集中保证的不变量 |
| --- | --- | --- |
| 输出管理 | Plan / Apply / Cleanup，操作绑定任务与运行代 | 输出归属、路径限制、碰撞、取消、写入原子性、仅删本任务文件 |
| 运行态管理 | Snapshot / Prepare / Commit / Retire | 有效配置来源、激活原子性、旧代退出、排队任务处理和待重启字段 |
| 文件操作 | Preview / Execute / RecoveryStatus | 默认不覆盖、稳定操作对象、计划版本、失败补偿、恢复记录 |

不要把 app.go 机械拆成大量相互引用的 handler。可先按运行态、配置、存储操作、Webhook、流与媒体路由拆文件，真正的规则下沉到上述模块；handler 只解析请求、授权和映射结果。

热更新有三条可选路线：

| 路线 | 收益 | 代价与选择 |
| --- | --- | --- |
| 有任务运行时拒绝应用相关修改 | 最容易消除跨代双写，行为明确 | 用户需等任务结束；适合作为首轮修复，不必拒绝完全无关的 UI 设置 |
| 暂停入队、取消并排空旧写入后切换 | 保留动态配置体验，交接可证明 | 必须先修复取消，并给退出设有界超时；超时应保留旧运行态并明确报告 |
| 按任务差量更新，未变任务与队列保持 | 避免保存无关设置就重启所有任务 | 需定义配置等价、存储依赖变化、旧请求策略；适合可靠性基线建立之后 |

建议短期采用第一条，随后实现第二条；第三条由实际热更新频率决定。长时间播放请求继续持旧存储快照，与写任务排空分开处理。排队与延迟任务不能静默丢弃，应选择迁移、取消并记录，或拒绝变更。

输出路径限制同样需要明确实现取舍：只做 `EvalSymlinks` 加字符串前缀检查不能封闭检查后替换窗口。若保持 Go 1.23，可在受支持系统上使用基于目录句柄的相对文件操作，并对不支持的系统提供明确策略；若升级 Go，应评估 `os.Root` 及目标版本具体提供的操作是否覆盖创建、改名和删除。不要未经验证就把版本升级当成完整修复。重命名默认不覆盖也需使用平台支持的原子语义或受控的存储级互斥，单次 `Lstat` 预检不足以防并发外部写入。

## 后续实施路径

### 第一阶段：阻断误删与越界

按依赖建议分为独立交付：

1. 前端存储快照与破坏性操作守卫，修复 R04；同时修复 R05 默认重命名覆盖。验收当前临时复现转为正式测试并通过。
2. 配置拒绝源/目标危险重叠、任务输出重叠；生成和工具统一路径约束，修复 R01—R03。短期选择明确拒绝共享输出，避免未完成清单前提供危险能力。
3. 在生成循环与清理中落实取消，修复 R06；再引入跨运行代写入协调修复 R07。验收旧代无法覆盖新代，取消后不进入同步清理。

退出条件：原有全部检查通过，上述数据安全用例通过，临时目录外文件和未知文件完整；不得用 UI 警告代替后端约束。

### 第二阶段：一致性与播放可靠性

- 统一 Config 的磁盘值、环境覆盖与有效快照，完整校验插件、JSON 和字段；修复 R08、R09、R12、R15、R16。
- 把热更新划为 prepare/commit/retire；记录 config generation、运行任务取消原因，以及代理和历史模块状态。UI 读取实际待重启字段。
- 分离 WebDAV 流与元数据超时；不在已发送媒体响应后拼 JSON 错误，传输失败通过连接行为与指标表达，修复 R10。
- Webhook 做路径覆盖集合与原子入队，修复 R11；共用生成计划修复 R13；在外部请求出口统一脱敏修复 R14。

退出条件：长时间 Range/HEAD 传输、取消与断线、端口占用导致失败回滚、环境 token 保存一致性、兄弟事件不丢失均有自动化证据。

### 第三阶段：输出清单与可恢复操作

输出清单记录 task ID、storage ID、源 locator、相对输出路径、生成摘要和运行代。清理只处理清单中的文件，发现内容已被手工修改时保留并报告。每次运行先计划后写入，只有完整扫描成功才推进清理。

存储格式有两个可行方案：

- 每任务原子 JSON 清单：部署简单、迁移轻，适合当前串行任务；大库每次重写成本较高，需要定义崩溃后的临时文件恢复策略。
- SQLite：可事务更新运行记录、输出归属、操作日志，适合多任务与大库；增加迁移、备份、驱动和构建选择成本。

建议先保持单体和独占输出根，用相同接口验证清单语义，再以十万条输出的耗时、峰值内存和恢复复杂度决定是否用 SQLite。不要同时维护两套相互独立的归属事实。共享输出只有在归属与冲突规则稳定后开放。

批量重命名预览应返回计划标识和源条目摘要；执行时校验快照，变化则返回冲突并要求重新预览。远端存储不支持事务时，不能承诺数据库式回滚；应暴露部分完成与恢复清单。

### 第四阶段：容量、依赖和真实兼容

- 前端先明确大目录分页/虚拟化策略，再考虑首次加载包优化。本次最大 JS 分块约 713 kB、gzip 230 kB；已有懒加载，优化应看浏览器测量。
- 调整 Vite/Vitest 等依赖到受维护版本，分步更新 lockfile 并跑完整构建测试。仅生产审计的 react-router 告警指向 RSC 模式，而当前应用是 SPA BrowserRouter，不能据此断言存在该线上攻击路径。工具链告警主要影响开发/测试环境，仍需修复。
- Go、Alpine、ffmpeg 的支持期和安全补丁单独核对；本轮未执行 govulncheck 或容器漏洞扫描，不能报告其无漏洞。

## 建议的下一次交付范围
